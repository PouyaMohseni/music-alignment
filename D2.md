# D2 — MIDI-Privileged Training (LUPI) on top of D1

Status: proposed + first implementation. Builds on D1 (same towers, same DTW
decode); adds two training-only signals derived from symbolic MIDI. **MIDI is
never an input at inference** — only the audio tower (now MIDI-informed) and
score tower run at test time, identically to D1.

---

## 0. The idea (Vapnik's Learning Using Privileged Information)

MSMD's audio is *synthesized from* MIDI — so for every training piece we have a
perfect, noise-free description of what's happening musically at every instant
(exact pitch, onset, duration), a description that is by construction
unavailable from real audio at inference (timbre/reverb/dynamics destroy exact
recoverability, and the whole point of the task is not to require symbolic
input). LUPI formalizes exploiting privileged information at *train* time to
shape a model that must operate without it at test time.

D1's first run diagnosed two concrete weaknesses this can attack directly:

1. **Diffuse per-frame CE.** Training CE only fell from 6.54 (random-init,
   ≈ln(629)) to ~5.15 — the model never got confident. Some of that
   "confusion" may be *correct*: repeated passages (literal score repeats,
   sequences, transposed restatements) are genuinely indistinguishable from
   audio content alone, so a hard single-column CE target actively punishes
   the model for a correct-but-alternate reading. MIDI tells us exactly when
   this is happening (identical/near-identical local pitch context at two
   different score positions) — information no audio-only model can access.
2. **Bimodal DTW error** (median 3.85s, mean 9.7s — close when right,
   catastrophic when wrong). Consistent with #1: the wrong-when-wrong cases are
   plausibly exactly the ambiguous repeated passages the loss should not have
   forced a single answer on.

Two independent mechanisms, both MIDI-train-only / audio-only-inference:

---

## 1. Repeat-aware soft CE labels (`mymodel/d2_midi_privileged/repeat_labels.py`)

For each training piece, using the whole-piece MIDI (`cpjku_fmt/performance/<piece>.mid`):

1. Build the note sequence sorted by onset: `(onset_frame, pitch)`.
2. For a sliding window of `k` consecutive notes (default k=5) ending at each
   onset, hash the **relative pitch-interval sequence** (transposition-
   invariant — repeats are often transposed) as an n-gram key.
3. Group score positions (columns, via the existing coords/onset_frames
   mapping) whose n-gram key matches. Positions in the same group are
   *musically indistinguishable from local audio content alone* — this is the
   privileged judgment call only MIDI can make.
4. At train time, `dense_ce_loss`'s per-frame Gaussian target (currently
   centered on the single true GT column) becomes a **mixture of Gaussians**,
   one centered on the true column and one on each equivalence-group member
   (weight `repeat_label_weight`, default 0.3, on alternates relative to the
   true column's 1.0 — the true position is still preferred, alternates are
   merely not punished as harshly).
5. **Nothing here touches inference.** The similarity matrix, DTW decode, and
   eval metric are byte-for-byte the same computation as D1 — only the
   *training target* changes.

This is a direct, symbolic-side generalization of the classical score-following
literature's repeat/jump handling (Arzt et al. explicitly special-case repeats
in their online DTW) — except here MIDI *automatically discovers* the repeat
structure instead of requiring hand-annotated jump markers.

---

## 2. MIDI→audio cross-modal distillation (`mymodel/d2_midi_privileged/midi_encoder.py`)

1. **MIDI encoder** `M`: per-frame active-pitch multi-hot vector (88 dims,
   same construction as B2's `pitch_roll` — see `extensions/hooks/pitch_patch.py`
   `_compute_pitch_roll`) → small `Linear(88→64)+GELU→Linear(64→d_model)` →
   L2-normalize. A frame with MIDI is an exact, zero-noise description of
   "what note(s) are sounding right now" — richer and cleaner than anything
   recoverable from a mel-spectrogram or MERT embedding alone.
2. **Distillation loss**: symmetric InfoNCE between the audio tower's output
   `A(t)` and the MIDI encoder's output `M(t)` at the same frame (same recipe as
   C4's tempo-contrastive InfoNCE, applied cross-modally instead of
   cross-tempo). Pulls the audio tower toward producing embeddings that already
   carry the discriminative content MIDI has for free, so the LEARNED audio
   representation approximates the privileged one as closely as raw audio
   allows.
3. `M` is a pure training-time scaffold: after training, `M`'s parameters are
   simply not loaded for inference/eval (D1's existing `eval.py` needs zero
   changes — it only ever imports `D1Model`, which is unchanged).

---

## 2. Combined loss

```
L = ce_soft(S, repeat_aware_targets)          # component 1, replaces D1's ce
  + dtw_weight   * soft_dtw_matrix_loss(S)     # unchanged from D1
  + distill_weight * midi_distill_loss(A, M)   # component 2, new
```

`distill_weight` default 0.2 (same CE-dominant discipline as D1's `dtw_weight`
— B3's lesson: never let an auxiliary loss outcompete the primary objective for
model selection).

---

## 3. Implementation plan

- `mymodel/d2_midi_privileged/repeat_labels.py` — MIDI parse (pretty_midi,
  already used by C4) → per-piece equivalence groups → soft target builder.
- `mymodel/d2_midi_privileged/midi_encoder.py` — `MidiEncoder` module + pitch-roll
  construction (reuses B2's exact frame-indexing convention).
- `mymodel/d2_midi_privileged/losses.py` — `soft_multi_target_ce_loss`,
  `midi_distill_loss`.
- `mymodel/d2_midi_privileged/data.py` — extends D1's `D1Piece` with `pitch_roll`
  (T, 88) and `repeat_groups` (dict: column → [alternate columns]).
- `mymodel/d2_midi_privileged/train.py` — same loop as D1's, swapping in the
  three-term loss and lazily-constructed `MidiEncoder`.
- `mymodel/d2_midi_privileged/eval.py` — **thin re-export of D1's eval.py**,
  unchanged, since inference never touches MIDI or `MidiEncoder`.
- `configs/d2_midi_privileged.yaml`, `train_d2_midi_privileged.sh` (A100, 24h,
  resume — same pattern as D1).

## 4. Risks

- Repeat-detection false positives (short/common pitch n-grams matching
  incidentally) would over-soften real target sharpness — mitigated by using a
  reasonably long window (k=5 notes) and requiring exact interval-sequence
  match, not just pitch-class overlap.
- Distillation could pull the audio tower toward pitch-only information and
  discard useful timing/timbre cues dense CE needs — mitigated by the small
  `distill_weight` and by `M` only ever being a soft pull (InfoNCE), not a hard
  constraint.
